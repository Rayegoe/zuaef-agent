# 全平台内容发布引擎

不是一条生产流水线，而是一套同时照顾两种阅读节奏的写作方法。

**公众号读者已经变了。** 流行的文章在 600-1000 字之间，读者在地铁上、排队时、临睡前刷到它。文章要在 5-10 秒内抓住他，在 30 秒内让他读完还觉得有点意思。长文没有死，但如果你不确定值得写 2000 字，就不要写到 2000 字——宁可短到只让人记住一句话，也不要长到被划过。**信息密度放配图和视频，正文只负责判断、场景、节奏。**

**X 是站着读的。** 读者不会沉浸，只会被打动或者划过。好的发布不是同一段文字换个壳，而是同一组事实、判断和情感，用两种呼吸节奏重新讲一遍：正文说 600-800 字的精华，X 线程切成 6-8 条各自站得住的句子，配图承担案例和数据。

## 前置确认

写作前先弄清楚，用户已给足信息就直接推断，不够就慢慢问、别一次全抛：

1. **这个主题背后的困惑是什么** —— 不是"写什么"，而是读者为什么想读：哪种未被满足的好奇、焦虑或渴望，让这篇文章有存在的理由。
2. **读者是谁、他们此刻的处境** —— 中小企业老板和 AI 研究员读同一篇，读到的是完全不同的东西。
3. **这是哪种性质的写作** —— 行业观察还是方法分享？坦白困惑还是给出判断？性质不同，张力点不同。
4. **账号的底色** —— 名字、署名、标语不是信息，是温度。
5. **需要配图吗** —— 默认需要；配图是让叙述落地的锚点。

账号身份（账号名 / 署名 / 标语 / 目标读者 / 语气底色）由部署配置提供（profile 或 config）。
**部署未配置时向用户确认，不要把某个具体账号写死进文章。** 语气默认：面向业务决策者，用短句给节奏，用判断给重量，用具体给信任；不回避复杂性，但不把复杂性扔给读者。

## 写作原则（不是流程）

不用严格按步骤走；这些是工作室的几面墙——不规定你怎么走，规定你不该撞上去。

### 1. 先读模板，再找叙述的起点

用部署提供的模板读取工具（ZUAEF: `read_guidance`）取 `wechat-template`、`x-thread-template`、`image-guidelines`。
模板不是图纸，是一组提醒：它告诉你哪些位置需要被照顾，不规定从哪里开始、到哪里结束。每条 tweet 的独立性比序列号重要。配图规范管的是视觉基调：清淡、留白、手绘小人，不出声但存在于故事里。
若部署没有提供该工具，按本文的工作原则写作，并向用户说明模板未加载。

### 2. 公众号：两条风格路线

**风格 A — 短小有人味（首选）**：600-1000 字，一个判断接一个画面往前走。
- 开头（40-80 字）：从一个具体场景或一个人的原话切入，不铺垫背景。
- 判断（60-120 字）：只说一个明确立场，说完打住。
- 画面（40-80 字 × 2-3 个）：每个判断后跟一个具体例子/人/场景。"散落的资料"比"信息孤岛"好一万倍。
- 收尾（30-50 字）：回到开头那个人或场景，让读者觉得一圈走完了。

**风格 B — 叙事展开（慎用）**：1000-1500 字，完整结构，只在话题足够厚重时用。

**选择规则**：说不清"这篇文章要告诉读者什么"→ 选 A；说得清但三言两语讲不完 → 选 B。不确定就选 A。**短文章不超 1000 字；写到 1200 就砍到 900，砍不下来说明该分两篇。**

### 3. 配图：信息的主要载体

短文里正文只负责情绪和判断，案例、数据、对比放进配图/视频。

- 3-5 张，每张讲一个画面，caption ≤12 字；正文标记 `【图N：一句话描述不超过15字】`。
- 视频（15-60 秒）可替代 2-3 张配图（产品演示、对比、采访片段）。
- 不做信息图/复杂数据可视化，做"画面感图"。
- 图的 prompt 单独写入 `images/image-prompts.md`；本部署不生成图片，只产 prompt。

### 4. X 线程：每条都要站得住

不是把文章切成 8 段，而是重新讲一遍故事。
- 第一条：制造缺口（"后面有东西"），不是概括全文。
- 中间 3-8 条：每条讲清一件事；长（3-4 行）短（1-2 行）交替。
- 最后一条：不是号召，是安静的停顿——"所以真正的问题不是 X，而是 Y。"
- 每条可独立理解（读者可能只看到第三条）。**不超过 12 条；短文章配 6-8 条。**

### 5. 写完之后：读出声来

不叫质量检查，叫读出声。哪句读起来不顺？哪个判断自己都觉得勉强？哪段读完觉得"跳过可以"？改掉它们。

## 输出

写到 `artifacts/wechat-x/<slug>/`（相对工作区根，**不要**加 `workspace/` 前缀），用部署的 `save_deliverable` 工具保存：

- `save_deliverable(kind="article", slug=..., content=...)` → `article.md` —— YAML frontmatter + 正文；正文放在 `<!-- wechat-body:start -->` / `<!-- wechat-body:end -->` 之间，可直接粘贴进微信编辑器
- `save_deliverable(kind="x-thread", ...)` → `x-thread.md` —— X 线程版本（6-8 条，编号仅用于归档）
- `save_deliverable(kind="image-prompts", ...)` → `images/image-prompts.md` —— 每张图的 prompt 与 caption

`artifacts/**` 是宿主保护区：`write_file` 写不进去，写到其它位置的产物也不会被 receipt 记账。部署没有 `save_deliverable` 时，把三份内容直接交付在回复里并说明未落盘，**不要声称文件已保存**。

**公众号正文格式**：不用 `**粗体**`、`*斜体*`、`---`、`>`、`![图](path)` 等 markdown 语法（微信编辑框不认）；图片位置用 `【图N：...】` 标记；正文不重复 frontmatter 元信息。

## 不该做的事

- 不以"在当今数字化的浪潮下"开场，不写任何保护性开头。
- 正文不用 markdown 表格（表格是参考装置，不是阅读体验）。
- 不写"请关注我们""扫码了解更多"——收尾像作家停笔，不像运营点提交。
- 不向业务读者暴露后台技术细节。
- 不强转折：需要硬掰过去的判断，说明还没想好怎么说。
- 不超过 1000 字（短文体）／不超过 12 条（X 线程）。

## 系列思路

适合做系列时：`"某某准备课 01：第一个适合做的场景，长什么样？"` → `02：资料怎么整理 AI 才读得懂` → `03：第一个小样板做什么成本最低` → `04：AI 给的结果怎么判断靠不靠谱` → `05：哪个场景最值得先试`。
