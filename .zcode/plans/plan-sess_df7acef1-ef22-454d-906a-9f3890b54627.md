# P3B-1 — Golden Failure Case 修复:authoring 任务直接呈现结果,不再误触外发审批

目标(你的两条核心规则落地):
> 读写/思考/研究/写作/改稿/存工作产物 = 工作过程,零审批;只有真正跨边界的 External Effect(发客户/发布/改生产数据)才审批。
> 用户要求"写/改/分析"时,默认 Outcome 是把结果呈现给当前用户(Supervisor),不是发给业务对象。

## 修复层(四层,全部在既有机制内,零新框架)

**1. 呈现契约:`RunSummary.deliverable`(核心修复)**
- `models.py` 给 `RunSummary` 加 `deliverable: str | None`——本次交付给当前用户的完整正文(如改写稿),与 `outcome` 同级:自由文本、不做 host 验证(呈现≠证据,证据仍是 verified artifacts/effects)。
- `render_terminal`:有 deliverable 时**正文优先**——先完整正文(chunk_text 自动分段),后接一行 meta(状态 emoji + Run id);**不再显示 counts**(counts 属 Console,`/status` 与 receipt 仍有)。无 deliverable 时保持现卡片。

**2. 指令边界:authoring ≠ customer delivery**
- Case `TOOLSET_INSTRUCTIONS` 重写关键段:写作/改稿/分析任务的默认终态 = `final_result` 带 `deliverable`(全文)+ `save_artifact` 落证;**只有用户明确表达外发意图**("发给客户/发出去/给他看/发群里")才 `save_draft → send_to_customer`;明确写出 `draft ≠ outbound draft`(save_draft 语义收窄为"准备客户外发稿")。
- Writing `WRITING_RULES` 增补同一规则(写作域任务以呈现给用户收尾)。

**3. 审批卡内容(机械兜底)**
- 即使模型仍误提外发,审批卡必须**显示将发送的草稿全文**:`_settle_paused` 在 host 侧读 `workspace/cases/<session.case_id>/drafts/<draft_ref>`(校验 `msg-*.md` 形状 + 路径不逃逸 drafts/),`render_pause` 渲染内容块(上限 ~2800 字,超出截断标注)。从此不存在"批了没看过的东西"。

**4. 验收红线(Golden Failure Case 落为测试)**
- `test_gateway_service.py` 新增金例:输入文章 + "改写这篇文章",scripted 模型走 `save_artifact → final_result(deliverable)` → 断言 **0 张审批卡**、surface 收到的主文本包含改写正文、receipt 保留 artifact 证据。
- renderer 测试:deliverable 优先布局、审批卡内容块。
- 真实模型验证:实现后用 /tmp 一次性脚本按金例输入跑一次 GatewayService(真实 LLM),确认新指令下 0 审批 + 正文返回;结果汇报,脚本不进仓库。托管网关重启后由你在 Telegram 复跑同例。
